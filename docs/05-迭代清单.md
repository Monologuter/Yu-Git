# 迭代清单

> 这份文件是 **agent 持续迭代的依据**，也是人看进度的地方。
>
> 存在的理由：新会话的 agent 读不到上一次会话的上下文。没有这份清单，
> 每次都要从代码里重新推断该做什么，而「为什么这么排优先级」「哪些已经
> 试过不行」这类信息根本推断不出来。
>
> **动了任何一项就回来更新状态。** 清单和代码不同步，比没有清单更糟——
> 那会让人照着过时的信息做决定。

## 怎么用

- 状态：`[ ]` 待办 · `[~]` 进行中 · `[x]` 完成 · `[-]` 放弃（写明理由）
- 每项都要有**验收标准**，否则「做完了」是没法判断的
- 优先级 P0 最高。P0 没清空之前不要开 P1
- 完成一项就 commit + push（提交信息用英文，见 `docs/04` §3）

## 需要人拍板的

分两类，无人值守时的处理方式不同。

### A 类 · 绝对不做（不是「问一下」，是不做）

- **不可逆操作**——`push --force`、改写已推送的历史、删分支、删 tag、吊销证书
- **对外发布**——打 tag、发 Release、改仓库描述、发布到任何外部服务
- **引入第三方依赖**——需要书面论证（`docs/04` §4）
- **许可证与商业模式**相关的任何改动
- **动 `server/` 的线上配置**——那是跑着的生产服务

### B 类 · 记下来继续走（无人值守时不要停在这里干等）

- **审美判断**——配色好不好看、间距舒不舒服，只有人看了才知道
- **优先级变更**——不要自行调整清单顺序
- **规格有歧义**——设计稿没说清、两处规格互相矛盾

处理方式：**按最合理的一种做法实现下去**，然后在清单末尾的
「待用户确认」区记一条，写明做了什么选择、为什么、以及要看哪里。
不要因为一个观感问题就停下整轮迭代。

## P1 · 基础操作缺口（最高优先，先于一切深化）

**盘点结论：我们把力气全花在差异化上，基础盘有洞。**

`GitOperation.Kind` 目前只有这些写操作：
`stage / unstage / stagePartial / unstagePartial / discard / commit / amend /
stashPush / stashPop / createBranch / switchBranch / deleteBranch / renameBranch /
merge / setUpstream / interactiveRebase`

下面四项是**每天都要用**的，缺了用户十分钟就退回终端——比缺任何 AI 功能都致命。
`docs/01` 当时列 table stakes 时漏掉了它们。

四项共用同一套骨架（`GitOperation` + `hazard` + 自动快照 + 危险预警 +
透明命令层），**一起做比分四次省事**。

- [x] **cherry-pick**
      - `GitOperation.cherryPick(hash:subject:)`，hazard `.none`
      - **冲突不是失败**。git 冲突时退出码是 1，走 `perform` 会被当错误抛出去，
        用户看到一句「操作失败」，而仓库其实正停在一个他能解决的地方。
        新增 `RepoActor.performAllowingConflict` 返回 `ReplayOutcome`，
        停在冲突上时界面切回「变更」栏——冲突文件就列在那儿，旁边是「解决…」
      - 判据用「仓库里有没有未合并文件」而不是退出码或 stderr 字样：
        退出码 1 还有别的成因，stderr 措辞随 git 版本变
      - 提交列表右键入口。**唯一不弹确认的一项**——只往历史加一条新提交，
        后悔了删掉就行；为它多设一道确认只会让人对真正该确认的那几个也麻木
- [x] **revert**
      - hazard `.none`，`--no-edit` 写在参数里而不是靠环境变量兜底：
        这条命令要展示给用户、也能被复制到终端跑，别人的终端里没有 `GIT_EDITOR=true`
      - 中文说明讲清了与 reset 的根本区别，并点明已推送的提交只能用 revert
- [x] **reset（三种模式）**
      - 三个工厂方法 + 三个 `GitOperation.Kind`（时间线是按 kind 决定拍不拍快照的）
      - `--hard` 的 hazard 是 `.discardsUncommittedWork`，快照由现有机制自动拍
      - **实测纠正了一处文案**：`git reset --hard` **不删未跟踪文件**。
        说反了比不说更糟——用户会以为新建的文件已经没了，转头去别处找。
        补了测试锁住这个行为和这句文案
      - 执行前校验目标是不是 HEAD 的祖先。历史列表用的是 `--all`，屏幕上确实会
        出现别的分支的提交，重置过去不是「退回走过的某个点」而是把分支整个搬走
- [x] **tag 创建 / 删除 / 推送**
      - 填了说明就打附注 tag，界面上说清了为什么发版必须用附注
        （只有它会被 `git describe` 计入，有测试锁住）
      - 侧栏 tag 右键：推送 / 删除本地。**删远程 tag 不放进这个顺手菜单**——
        它影响的是别人，已经拉过的人本地那份不会消失。操作已实现
        （`deleteRemoteTag`，hazard 比删本地高一档），但要另找入口
      - 顺带修正了 `.rewritesHistory` 的通用预警文案：原文说「这些提交会得到新的
        commit hash」，那对 amend/rebase 成立，对 reset 不成立（reset 挪的是分支指针，
        提交本身没变）。把这句话移进 rebase 自己的说明里，通用文案改成三者都为真的说法

其余基础缺口：

- [x] **stash 完整管理**（现在只有 push/pop，看不见里面有什么）
      - `git stash list --format="%gd%x1f%s%x1f%ct%x1f%H" -z` 解析
      - **实测得来的坑**：subject 有两种形态，前缀不同，只认一种会把分支名
        连着说明一起显示出来
        ```
        WIP on master: 78f2b67 base   ← 没给说明时 git 自动生成
        On master: 改了一半的功能       ← 用户 -m 填了说明
        ```
        「WIP on 」必须**先于**「On 」匹配，否则 On 会先命中前者里的 on，
        把分支名切成「 master」
      - 自动生成的描述说的是「储藏时 HEAD 在哪」而不是「储藏里改了什么」，
        界面上要能区分，并提示用户补说明
      - **`stash@{N}` 的 N 会变**：删掉中间任何一条，后面所有索引都往前挪。
        读出来的索引只在那一刻有效，不能存起来隔一会儿再用
      - apply（保留）与 pop（应用后删除）要分开给，拿不准时用 apply
      - 验收：能看列表、看每条改了哪些文件、预览 diff、apply/pop/drop
      - **落地时又实测出两个坑**：
        1. 一条只装着未跟踪文件的 stash，`git stash show` 不带 `--include-untracked`
           会返回**空输出且退出码 0**——界面上就成了「这条是空的」，而它好好装着东西。
           不带这个参数的版本看不出任何异常，只能靠实测发现
        2. `git stash drop` **不认 hash**（报 "is not a stash reference"），
           只认 `stash@{N}`；而 `apply`/`show` 认 hash。所以躲不开索引，
           只能在写队列**内部**用 hash 现查一次位置再执行——查完到执行之间
           放在队列外仍然能被插队。已被 drop 的 stash 没有正常途径找回来
      - 「WIP on 」优先于「On 」这条其实用 `hasPrefix` 就自然成立，
        清单原文描述的误判只在用「包含」判断时才会发生。测试两种都锁了
      - 面板挂在 ⌘K「储藏」下。apply 是默认按钮，pop 排它后面——拿不准时该用 apply
- [x] **remote 管理**（现在只能读）——add / remove / rename / 改 URL
      - 四个都只改配置不动提交，hazard 一律 `.none`，需要确认的地方用
        `confirmationDialog`，和删分支的做法一致。归进 hazard 体系的话，
        时间线会为每次改 URL 拍一张工作区快照，毫无意义
      - **删除远程的真正后果**：连带删掉 `refs/remotes/<name>/*` 下的全部远程跟踪分支。
        本地分支不受影响，但那些只在远程存在、从没建过本地分支的提交，
        删完就没有引用指向了。文案和测试都锁了这一条
      - 改名会让远程跟踪分支跟着搬家、本地分支的 upstream 一并更新（有测试）
      - 面板挂在 ⌘K「远程管理」下。push URL 与 fetch URL 不一致时用警示色标出来——
        那个配置很少见，不标的话用户可能推到自己没料到的地方
- [x] **submodule**——状态显示、更新、递归操作
      - 面板挂在 ⌘K「子模块」下：状态、记录的提交、签出的引用，一键更新
      - **`git submodule status` 的状态字符是第一列，正常时是一个空格。**
        随手 trim 掉行首空白，「已同步」就会和别的状态混在一起——剩下的部分
        长得一模一样。有测试锁这一条
      - 「未初始化」单独讲清楚：克隆父仓库时没带 `--recursive` 就是这个状态，
        而这是「代码拉下来编译不过」最常见的原因之一
      - 更新默认带 `--init`——「更新」在用户脑子里就包含「先弄下来」，
        而没初始化恰恰是最常见的那种需要更新的状态
      - 写测试时踩到的坑：`TemporaryRepository` 析构时删目录，
        用 `let (parent, _)` 接住子仓库等于当场把子模块的来源删了，
        `submodule update` 自然克隆不到
- [x] **LFS**——至少要识别并正确显示，不能把指针文件当普通文本
      - `LFSPointer` 解析那三行固定格式，diff 视图认出「一对指针的替换」时
        换掉按行 diff，改成说真事：多大、换成了什么、内容不在这儿
      - **这就是这一项存在的全部理由**：照常按行比的话，屏幕上是「改了三行字」，
        而实际是一个上百 MB 的二进制文件被整个换掉
      - 大小上限（1 KB）既是省事也是安全边界：没有它，一个恰好以
        `version https://…` 开头的几百 MB 文本文件会被整个读进来做匹配
      - 「哪些路径走 LFS」问 `git check-attr` 而不是自己解析 `.gitattributes`：
        属性规则可以出现在任意层级，还能被 `.git/info/attributes` 和全局配置覆盖
      - 判断仓库用不用 LFS 看 `.gitattributes`，**不看 git-lfs 装没装**：
        用 LFS 的仓库在没装 git-lfs 的机器上照样是用 LFS 的仓库，
        而那正是最该提示用户的时候（工作区里躺的是指针不是真文件）
- [x] **GPG 签名提交**——`docs/01` 点名 ugit 因缺这个被批评
      - 设置页（⌘K「提交签名」）可配 `commit.gpgsign` / `gpg.format` / `user.signingkey`，
        并说清只写进这个仓库的 `.git/config`
      - **这一页真正的价值是在配错之前拦住。** 开了签名却缺东西，之后每一次提交
        都直接失败，而用户看到的只是「提交失败」，完全联想不到是在这里做的事。
        实测发现有**两种**失败方式，报错完全不同：
        1. `gpg.format=ssh` 且没有 `user.signingkey` → `fatal: either user.signingkey ...`
        2. `gpg.format=openpgp`（默认）且本机没装 gpg → `error: cannot run gpg`
        第二种是写测试时才发现的——我原本只想到缺 key 那一种。key 配得好好的，
        签名照样失败，因为根本没有 gpg 可跑
      - 提交详情显示签名徽章。**`%G?` 绝不能进历史列表的格式串**：
        它会让 git 对每一条提交实际跑一次验签，5 万条的首屏直接崩掉。
        做成选中某条时的单条查询
      - 状态判定上，`U`（签名有效但 key 未标记可信）**不算问题**：那是别人签的
        提交最常见的状态，跟「签名是坏的」混为一谈这个功能就成了噪音。
        `N`（未签名）也不报警——绝大多数提交都没签名，全挂警告等于没有警告
- [x] **init 新仓库**
      - 入口在欢迎页（唯一「手上还没有仓库」的地方）
      - **事前检查是这一项的全部价值**。`git init` 在两种情况下会一声不吭做出
        用户没想要的事，且都以 0 退出：
        1. 目录已经是仓库 → 打印 "Reinitialized" 并重新初始化一遍，
           用户以为自己新建了一个
        2. 目录在别的仓库里面 → 静默造出**嵌套仓库**，里层独立，
           外层只把它看成一个未跟踪目录
        两种都拦下来并说清楚；「目录非空」只提醒不拦
      - 默认分支名**显式给出**（`--initial-branch main`）。不给的话取决于用户的
        `init.defaultBranch`，同一个 app 在两台机器上会建出 main 和 master 两种仓库
- [x] **单文件历史**——某个文件的所有改动记录
      - 默认带 `--follow` 跨过改名。不带的话历史会在改名那一刻**戛然而止**——
        一个存在了三年、中途换过名字的文件，看起来像上个月才创建的
      - `--follow` **只接受一个 pathspec**（给两个会 fatal），所以是独立方法，
        没有复用 `log(paths:)` 的数组参数
      - 入口在变更列表的文件右键
- [x] **分支对比**——两个分支之间差了哪些提交
      - 提交用两点（`base..target` 和反向各一次），**文件差异必须用三点**。
        两点比的是两个尖端，会把 base 独有的文件列成「被删除」——
        一个刚分出来加了一个文件的分支，用两点看会显示成「加了 1 个，
        删了 main 后来加的 8 个」。留了一条对照测试记录两点错在哪
      - 没有共同祖先（`--orphan` 那种）时返回 nil 而不是报错，界面说明
        「这两条分支没有共同起点」——那是事实，不是故障
      - 入口在侧栏分支右键

## P1.5 · 借鉴 GitKraken（功能抄惯例，体验接我们的四样）

**原则**：功能本身照搬 GitKraken 的交互惯例（那是几十年沉淀，没必要重新发明），
但每一个都接上它没有的四样——时间线快照、危险预警、透明命令层、AI 中文解释。

| 操作 | 接上什么 |
|---|---|
| cherry-pick | 冲突走 AI 三方合并；操作前快照，失败一键回退 |
| revert | AI 用中文解释「这次 revert 会撤掉什么」；预览反向 diff |
| reset --hard | 危险预警三答，其中「能撤」这个答案靠时间线才第一次成立 |
| tag | 透明命令层显示等价命令；删已推送 tag 时警告影响他人 |
| stash | 内容进时间线；AI 给每条生成中文摘要（`stash@{3}` 三天后没人记得是什么） |

- [~] **多仓库切换器**——最近仓库 + 快速切换 + 跨仓库搜索。
      **不做** GitKraken 的 Workspaces 抽象：那是给团队协作设计的，
      我们的用户多是个人同时开 3–5 个项目
      - 切换器已做（⌘⇧O），全键盘可用——切仓库恰恰是最不该摸鼠标的操作，
        它发生在你正打算干别的事的路上
      - 每一行显示该仓库当前在哪个分支。**为此直接读 `.git/HEAD`**
        （`RepositoryGlance`），不各开一次仓库：十个仓库就是十次 git 进程启动，
        而这个面板可能只是被扫一眼就关掉
      - worktree 与 submodule 里的 `.git` 是**文件**不是目录，读不到 `HEAD`，
        这时返回 nil 不显示分支——猜错分支名比不显示更糟
      - **跨仓库搜索还没做**，那是这一项剩下的部分
- [x] **Issue 引用识别**——提交信息里的 `#123` 变可点链接。
      **不做**完整 issue 管理，那是网页和 IDE 的地盘
      - **不显示标题与状态**（原文写了）：那要为每条可见提交发一次 API 请求，
        滚动历史就成了刷接口，还得处理鉴权、限流、私有仓库。
        点开链接就到网页了，收益不值这个复杂度。记在这里以便回头推翻
      - 识别规则刻意收紧，宁可漏也不误报：`C#7`、颜色值 `#4A3D8B`、`abc#12`、
        `#12a`、`#007` 全部不算。**把不是引用的东西变成链接，比不变成链接烦人得多**——
        点开是 404，用户会以为 issue 被删了
      - GitLab 的路径是 `-/issues`，少那个 `-` 就 404；GitHub 与 Gitee 是 `/issues`。
        认不出平台或纯本地仓库时只显示文本，不给链接
      - `webBase` 里剥 `.git` 与结尾斜杠的**顺序**要紧：先剥 `.git` 的话，
        `repo.git/` 里的 `.git` 被斜杠挡着剥不掉。测试抓到的
- [x] **外部 diff / merge 工具集成**——尊重用户已配好的 `difftool` / `mergetool`
      - 读用户已有的 `diff.tool` / `merge.tool`，没配就**不显示那个菜单项**——
        摆一个点了没反应的入口比没有更糟
      - **`-y` 不能省。** 不带它 git 会对每个文件在 stdin 上问
        `Launch 'xxx' [Y/n]?` 并一直等下去——从 GUI 调起就是永久挂死，
        而那个提问根本没人看得到
      - **不走 `RepoActor.perform`**：那条队列是串行的，而 difftool 会一直阻塞到
        用户关掉工具窗口，放进队列等于在此期间冻结所有其他操作。而且这不是
        我们发起的写——mergetool 改的是工作区文件，性质上和用户在 Vim 里改了个
        文件一样，由文件监听器发现即可
      - `--tool-help` 的用户自定义段条目形如 `mytool.cmd <命令>`，工具名要去掉
        `.cmd`，否则 `--tool sourcetree.cmd` 认不出来
      - **顺带补上了单文件历史的右键入口**：那一项之前标了完成，但菜单项其实
        没插上（脚本替换的模式没匹配，我没验证）。两处菜单现在共用同一个
        `fileMenuExtras`，只在一边加会让人以为功能取决于文件暂存没暂存

**明确不抄的**：内置终端（用户已有终端，且我们的定位是「GUI 补充 CLI」
而非取代）、团队 Insights 统计（面向管理者，不是我们的用户）、
Cloud Patches（需要服务端，且与「不上传用户代码」的隐私承诺冲突）。

## P2 · 深化差异化（护城河）

这几项 GitKraken 没有、也不太可能做。

- [~] **时间线深化**
      - [x] 恢复前预览：告诉用户「退回这个点，工作区会变成什么样」（现在是盲跳）
        - `SnapshotPreview` 分三栏：**会被删掉**（快照之后新建的）、会被覆盖、会被写回来。
          「会被删掉」排最前——那是最需要看清的一栏
        - 确认按钮写清后果（「恢复，并丢弃 N 个文件的当前内容」），不是一个「确定」
        - **只跑三条 git 命令，不按文件逐个跑**：`ls-tree -r` 拿快照里全部 blob hash、
          `ls-files` 拿工作区清单、`hash-object --stdin-paths` 一次算完待比对的。
          逐个起进程的话几千个文件要几十秒，而这个预览要在对话框弹出那一刻就显示
        - 有一条测试专门验「预览说的和实际恢复的结果一致」——说一套做一套的预览
          比没有预览更糟
      - [x] 选择性恢复：只恢复某几个文件
        - 真实场景是「agent 把这一个文件改坏了，但另外三个改得挺好」。
          只能全量恢复的话，用户宁可手工去改，时间线就白做了
        - 预览面板的每一栏可整组勾选，也可逐个勾。默认全选——整个退回去
          仍是最常见的意图，勾选是给例外用的
        - **和全量恢复的关键差别：不动 index。** 全量恢复会把 index 退回 HEAD；
          选择性恢复是外科手术，动了 index 会让用户已经暂存好的其他文件
          莫名其妙掉出暂存区。全选时仍走全量恢复，因为「整个回到那一刻」
          本就该带上 index
      - [x] 快照语义标注：「Claude 第 3 轮改动前」而不是「操作 17」
        - 用 `git notes --ref=refs/yugit/timeline-labels`，不自己存 JSON：
          notes 天生就是「给 commit 挂附加文字」的机制，能被 git 正常遍历、
          gc 时不丢、不用自己处理并发写
        - 走**私有 ref** 而不是默认的 `refs/notes/commits`——后者是用户的地盘，
          且默认显示在 `git log` 里，塞进去会让用户的历史平白多出一堆
          「执行 xxx 之前」。有测试锁住「不落进用户自己的 notes」
      - [x] 快照过期策略：现在会无限堆积
        - `prune(keeping: 50)` 本来就在每次记录后跑，但有个真问题：
          **纯按数量会把用户特意标注过的那张删掉**，而那恰恰是最不该删的
        - 改成标注过的不计入配额也不参与淘汰。规则简单到能一句话说清：
          「起过名字的会一直留着」
- [ ] **Commit Composer 深化**
      - 按语义边界而非文件边界拆（同一文件的两处改动可能属于不同提交）
      - 提交顺序建议：让每个中间状态都能编译通过，否则 bisect 无意义
      - 拆完之后每个 commit 各自过一遍 AI 评审
- [ ] **worktree 变成 agent 指挥台**
      - 每个 worktree 显示对应的 agent 会话状态
      - 跨 worktree 的改动汇总，一屏看全
      - 冲突预警：两个 agent 改了同一文件时提前告警
- [x] **归因 blame 深化**——从「这行是 AI 写的」到「哪次对话、哪个 prompt」
      - **先得承认一件事：今天的提交信息里根本没有会话信息。** Claude Code 只写
        工具名和一个链接，不带 session id，也不带 prompt。靠解析提交信息
        答不出这个问题——得先有地方让 agent 把它写下来
      - 所以做的是**记录机制**：`AISession` 存进私有 notes（`refs/yugit/ai-sessions`），
        写入口是 MCP 工具 `yugit_attribute`，agent 提交完调一次。
        没记录时 blame 退回今天的行为（只说工具名），不假装知道自己不知道的事
      - prompt 走 stdin 而不是 `-m` 参数：那是用户写的任意文本，可能很长、
        有换行有引号，走参数会撞命令行长度上限
      - 读取是**批量**的：`notes list` + `cat-file --batch` 两条命令读完全部。
        一屏 blame 可能涉及几十个 commit，逐条 `notes show` 就是几十次进程启动
      - 工具描述里明确要求**只传这一轮的指令，不要传整段对话**——
        内容会存进 git 跟着仓库跑到任何人手上，而对话里往往有用户的私密信息
      - 端到端验过：agent 记完之后 blame 那一行显示当时的指令，
        且用户自己的 `refs/notes/commits` 没被碰
- [x] **MCP Server**（我认为差异化最大的一项）
      - 新包 `Packages/MCPKit`，含可执行文件 `yugit-mcp`，走 stdio。零第三方依赖，
        JSON-RPC 2.0 自己实现（约 200 行）。配置方式见该包的 README
      - **四个工具**：`yugit_snapshot`（拍快照）、`yugit_timeline`（列时间点）、
        `yugit_restore`（退回）、`yugit_explain`（问某条 git 操作危不危险）
      - 挑选标准是**只给 agent 做不到、或很容易做错的事**。agent 已经能直接跑
        `git status`、`git log`，包一层没有价值，还让工具列表变长、模型选错。
        快照这件事它做不到——Claude Code 的 checkpoint 只管它自己写过的文件，
        用户同时在编辑器里改的、终端里跑 git 造成的改动，它都不管
      - **两条安全约束**：`yugit_explain` 走白名单不接受自由拼装的 git 命令
        （这个 server 能写用户仓库，让模型自由拼命令行等于交出一把没保险的枪）；
        `yugit_restore` 按 id 精确匹配不做模糊查找（覆盖工作区，猜错的代价是几小时的活）
      - 协议层与 IO 层分开，最容易错的几处全在协议层且都有测试锁着：
        通知不许回响应、id 是数字就得回数字、**工具自己失败不是协议错误**
        （要回 `isError` 结果，回 JSON-RPC error 的话客户端会认为 server 挂了）、
        响应必须压成一行（stdio 按换行分隔消息，正文里出现换行会把一条切成两条）
      - 端到端验过：agent 打快照 → 改坏三个文件（含删掉一个未提交的草稿）→
        退回去，草稿原样回来、多余文件被删掉

## 明确不做

写在这里是为了避免反复讨论。

- **Windows / Linux**——核心卖点之一是「原生」，跨平台等于放弃它。
  GitKraken 就是前车之鉴
- **上 App Store**——沙盒会限制对任意路径 git 仓库的访问
- **对基础功能收订阅**——`docs/02` 的商业模式铁律，本地 Git 全功能永久免费
- **自绘控件替代系统控件**——那是 Electron 应用的做法，我们的差异点恰好相反
