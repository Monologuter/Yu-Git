# 迭代清单

> 这份文件是 **agent 持续迭代的依据**，也是人看进度的地方。
>
> 存在的理由：新会话的 agent 读不到上一次会话的上下文。没有这份清单，
> 每次都要从代码里重新推断该做什么，而「为什么这么排优先级」「哪些已经
> 试过不行」这类信息根本推断不出来。
>
> **动了任何一项就回来更新状态。** 清单和代码不同步，比没有清单更糟——
> 那会让人照着过时的信息做决定。

## 怎么用

- 状态：`[ ]` 待办 · `[~]` 进行中 · `[x]` 完成 · `[-]` 放弃（写明理由）
- 每项都要有**验收标准**，否则「做完了」是没法判断的
- 优先级 P0 最高。P0 没清空之前不要开 P1
- 完成一项就 commit + push（提交信息用英文，见 `docs/04` §3）

## 需要人拍板的

分两类，无人值守时的处理方式不同。

### A 类 · 绝对不做（不是「问一下」，是不做）

- **不可逆操作**——`push --force`、改写已推送的历史、删分支、删 tag、吊销证书
- **对外发布**——打 tag、发 Release、改仓库描述、发布到任何外部服务
- **引入第三方依赖**——需要书面论证（`docs/04` §4）
- **许可证与商业模式**相关的任何改动
- **动 `server/` 的线上配置**——那是跑着的生产服务

### B 类 · 记下来继续走（无人值守时不要停在这里干等）

- **审美判断**——配色好不好看、间距舒不舒服，只有人看了才知道
- **优先级变更**——不要自行调整清单顺序
- **规格有歧义**——设计稿没说清、两处规格互相矛盾

处理方式：**按最合理的一种做法实现下去**，然后在清单末尾的
「待用户确认」区记一条，写明做了什么选择、为什么、以及要看哪里。
不要因为一个观感问题就停下整轮迭代。

## P1 · 基础操作缺口（最高优先，先于一切深化）

**盘点结论：我们把力气全花在差异化上，基础盘有洞。**

`GitOperation.Kind` 目前只有这些写操作：
`stage / unstage / stagePartial / unstagePartial / discard / commit / amend /
stashPush / stashPop / createBranch / switchBranch / deleteBranch / renameBranch /
merge / setUpstream / interactiveRebase`

下面四项是**每天都要用**的，缺了用户十分钟就退回终端——比缺任何 AI 功能都致命。
`docs/01` 当时列 table stakes 时漏掉了它们。

四项共用同一套骨架（`GitOperation` + `hazard` + 自动快照 + 危险预警 +
透明命令层），**一起做比分四次省事**。

- [ ] **cherry-pick**
      - `GitOperation.cherryPick(hash:)`，hazard `.none`（只加新提交，不动已有历史）
      - 冲突时接到现有的三方合并编辑器
      - 提交列表右键入口
      - 验收：能把任意提交挑到当前分支；冲突能解；时间线里有记录可撤
- [ ] **revert**
      - hazard `.none`（生成反向提交，原提交仍在）
      - 中文说明要讲清 revert 与 reset 的根本区别：
        revert 是「记录下我撤销了它」，reset 是「当它没发生过」；
        **已推送的提交只能用 revert**
      - 验收：反向 diff 可预览；生成的提交信息可编辑
- [ ] **reset（三种模式）**
      - **必须拆成三个工厂方法而不是一个带参数的**，让调用方在写代码时
        就得想清楚要哪种：
        - `--soft` → 只移指针，index 与工作区不动，hazard `.rewritesHistory`
        - `--mixed` → 移指针 + 清 index，工作区内容不变，同上
        - `--hard` → 全部重置，hazard **`.discardsUncommittedWork`**
      - `--hard` 是整个 app 最危险的一条命令。危险预警的三答里，
        「能不能撤」这个答案**只有靠时间线快照才成立**——
        reflog 能找回被跳过的提交，找不回还没提交的改动
      - 验收：三种模式各自的后果说明准确；`--hard` 前必定有快照
- [ ] **tag 创建 / 删除 / 推送**
      - 现在只能读（`RefParser` 解析），不能写
      - 有说明就打附注 tag（`-a -m`）：附注 tag 带作者日期说明，
        且只有它能被 `git describe` 正确处理，发版必须用它
      - 删除已推送的 tag 要明确警告会影响他人
      - 验收：能在任意提交上打 tag；轻量/附注两种都支持

其余基础缺口：

- [ ] **stash 完整管理**（现在只有 push/pop，看不见里面有什么）
      - `git stash list --format="%gd%x1f%s%x1f%ct%x1f%H" -z` 解析
      - **实测得来的坑**：subject 有两种形态，前缀不同，只认一种会把分支名
        连着说明一起显示出来
        ```
        WIP on master: 78f2b67 base   ← 没给说明时 git 自动生成
        On master: 改了一半的功能       ← 用户 -m 填了说明
        ```
        「WIP on 」必须**先于**「On 」匹配，否则 On 会先命中前者里的 on，
        把分支名切成「 master」
      - 自动生成的描述说的是「储藏时 HEAD 在哪」而不是「储藏里改了什么」，
        界面上要能区分，并提示用户补说明
      - **`stash@{N}` 的 N 会变**：删掉中间任何一条，后面所有索引都往前挪。
        读出来的索引只在那一刻有效，不能存起来隔一会儿再用
      - apply（保留）与 pop（应用后删除）要分开给，拿不准时用 apply
      - 验收：能看列表、看每条改了哪些文件、预览 diff、apply/pop/drop
- [ ] **remote 管理**（现在只能读）——add / remove / rename / 改 URL
- [ ] **submodule**——状态显示、更新、递归操作
- [ ] **LFS**——至少要识别并正确显示，不能把指针文件当普通文本
- [ ] **GPG 签名提交**——`docs/01` 点名 ugit 因缺这个被批评
- [ ] **init 新仓库**
- [ ] **单文件历史**——某个文件的所有改动记录
- [ ] **分支对比**——两个分支之间差了哪些提交

## P1.5 · 借鉴 GitKraken（功能抄惯例，体验接我们的四样）

**原则**：功能本身照搬 GitKraken 的交互惯例（那是几十年沉淀，没必要重新发明），
但每一个都接上它没有的四样——时间线快照、危险预警、透明命令层、AI 中文解释。

| 操作 | 接上什么 |
|---|---|
| cherry-pick | 冲突走 AI 三方合并；操作前快照，失败一键回退 |
| revert | AI 用中文解释「这次 revert 会撤掉什么」；预览反向 diff |
| reset --hard | 危险预警三答，其中「能撤」这个答案靠时间线才第一次成立 |
| tag | 透明命令层显示等价命令；删已推送 tag 时警告影响他人 |
| stash | 内容进时间线；AI 给每条生成中文摘要（`stash@{3}` 三天后没人记得是什么） |

- [ ] **多仓库切换器**——最近仓库 + 快速切换 + 跨仓库搜索。
      **不做** GitKraken 的 Workspaces 抽象：那是给团队协作设计的，
      我们的用户多是个人同时开 3–5 个项目
- [ ] **Issue 引用识别**——提交信息里的 `#123` 变可点链接，显示标题与状态。
      **不做**完整 issue 管理，那是网页和 IDE 的地盘
- [ ] **外部 diff / merge 工具集成**——尊重用户已配好的 `difftool` / `mergetool`

**明确不抄的**：内置终端（用户已有终端，且我们的定位是「GUI 补充 CLI」
而非取代）、团队 Insights 统计（面向管理者，不是我们的用户）、
Cloud Patches（需要服务端，且与「不上传用户代码」的隐私承诺冲突）。

## P2 · 深化差异化（护城河）

这几项 GitKraken 没有、也不太可能做。

- [ ] **时间线深化**
      - 恢复前预览：告诉用户「退回这个点，工作区会变成什么样」（现在是盲跳）
      - 选择性恢复：只恢复某几个文件
      - 快照语义标注：「Claude 第 3 轮改动前」而不是「操作 17」
      - 快照过期策略：现在会无限堆积
- [ ] **Commit Composer 深化**
      - 按语义边界而非文件边界拆（同一文件的两处改动可能属于不同提交）
      - 提交顺序建议：让每个中间状态都能编译通过，否则 bisect 无意义
      - 拆完之后每个 commit 各自过一遍 AI 评审
- [ ] **worktree 变成 agent 指挥台**
      - 每个 worktree 显示对应的 agent 会话状态
      - 跨 worktree 的改动汇总，一屏看全
      - 冲突预警：两个 agent 改了同一文件时提前告警
- [ ] **归因 blame 深化**——从「这行是 AI 写的」到「哪次对话、哪个 prompt」
- [ ] **MCP Server**（我认为差异化最大的一项）
      - 把驭Git 的能力暴露给 Claude Code：打快照、拆提交、查时间线
      - 意义在于**方向反转**：现在是驭Git 调 AI，MCP 让 Claude Code 调驭Git。
        GUI 成为 agent 的操作台，而不是 agent 的替代品——
        这才是 slogan「AI 帮你写代码，驭Git 帮你驾驭它」真正兑现的样子
      - GitKraken 做不了这件事，因为它不在开发者的终端工作流里

## 明确不做

写在这里是为了避免反复讨论。

- **Windows / Linux**——核心卖点之一是「原生」，跨平台等于放弃它。
  GitKraken 就是前车之鉴
- **上 App Store**——沙盒会限制对任意路径 git 仓库的访问
- **对基础功能收订阅**——`docs/02` 的商业模式铁律，本地 Git 全功能永久免费
- **自绘控件替代系统控件**——那是 Electron 应用的做法，我们的差异点恰好相反
