# 驭Git 工程规范

> 生产级项目的工程约定。原则：**能自动化的一律自动化，不能自动化的写成检查清单**——靠自觉执行的规范等于没有规范。
> 与本文冲突时，工程层面以本文为准；产品层面以 `02-产品需求文档.md` 为准。

## 1. 分支管理

### 1.1 分支模型：轻量 GitHub Flow

`main` 是唯一长期分支，**始终可构建、测试全绿**——任何时刻 checkout 出来都能跑。其余分支短期存在，合入即删。

### 1.2 什么时候开分支

| 直接提 main | 必须开分支 |
|---|---|
| 文档、注释、typo | 新模块 / 新 Package |
| 单文件小修复 | 需要多个 commit 才自洽的功能 |
| 已被测试覆盖的小改动 | 危险重构（写操作路径、patch 生成、并发模型） |
| 配置与脚本调整 | 试验性方案（可能整体废弃） |

判断标准很简单：**这次改动中途会不会让 main 处于不可构建或测试不绿的状态**。会，就开分支。

### 1.3 分支命名

`<type>/<kebab-case 英文描述>`，与提交的 type 保持同一套词汇：

```
feat/commit-composer      fix/index-lock-race
refactor/diff-parser      perf/log-streaming
spike/timeline-snapshot   # 试验分支，允许废弃不合并
```

用英文——分支名要进 CLI、GitHub UI 和各种脚本，中文分支名在这些场景里易出问题。

### 1.4 合并策略：rebase 保持线性

```bash
git switch feat/xxx
git fetch origin
git rebase origin/main     # 就地解决冲突
swift test                 # rebase 后必须重跑：冲突解决可能引入问题
git switch main
git merge --ff-only feat/xxx
git branch -d feat/xxx
```

**不产生 merge commit。** 理由不只是"好看"：这个项目自己就是 Git 客户端，线性历史让我们能在自家的 commit graph 上验证渲染效果，也让 `git bisect` 定位回归时不会掉进合并分支的迷宫。

已推送的分支若需 rebase，用 `git push --force-with-lease`（绝不用 `--force`，前者会在远程有他人新提交时拒绝）。

### 1.5 main 的不可协商约束

- 每个 commit 都能独立构建、测试全绿——这是 `git bisect` 可用的前提
- 不 force push。唯一例外：推送前发现敏感信息泄露
- 不提交注释掉的代码、调试 `print`、临时文件

## 2. 版本与 Tag

### 2.1 版本号

SemVer 与 PRD 的产品节奏对齐：

| 版本 | 阶段 |
|---|---|
| `0.1.0` – `0.3.x` | 内部 Alpha（能自用的基础盘） |
| `0.5.x` | 公开 Beta（时间线 Undo + AI 基础） |
| `1.0.0` | 正式发布（主打故事完整） |

1.0 之前：MINOR 表示里程碑，PATCH 表示修复。
1.0 之后：严格 SemVer——MAJOR 破坏性变更、MINOR 向后兼容的新功能、PATCH 修复。

### 2.2 Tag

- 格式 `v0.1.0`，带 `v` 前缀
- **一律用附注 tag**（`git tag -a`），不用轻量 tag——附注 tag 带作者、日期与说明，且 `git describe` 才能正确处理
- 预发布：`v0.5.0-beta.1`、`v1.0.0-rc.1`
- tag 只打在 `main` 上，且必须通过 §11 的发布检查清单

```bash
git tag -a v0.1.0 -m "v0.1.0 内部 Alpha：只读浏览"
git push origin v0.1.0
```

### 2.3 macOS 构建号

- `CFBundleShortVersionString` = SemVer（`0.1.0`），给用户看
- `CFBundleVersion` = **单调递增整数**，每次发布 +1，永不重置

macOS 判断"是否有更新"看的是 `CFBundleVersion`。一旦重置或回退，已安装用户将收不到更新——这是无法通过发新版修复的错误。

## 3. 提交规范

### 3.1 格式

Conventional Commits，正文用中文：

```
<type>(<scope>): <50 字以内的中文摘要>

<正文：为什么这么改，而不是改了什么>

<脚注：BREAKING CHANGE / Closes #12>
```

### 3.2 type

| type | 用途 |
|---|---|
| `feat` | 新功能 |
| `fix` | 修复缺陷 |
| `perf` | 性能优化 |
| `refactor` | 重构，不改变外部行为 |
| `test` | 只动测试 |
| `docs` | 只动文档或注释 |
| `style` | 只动格式（缩进、空行），无逻辑变化 |
| `build` | 构建系统、依赖、签名配置 |
| `chore` | 杂项（.gitignore、hooks、脚本） |
| `revert` | 回滚 |

### 3.3 scope

按模块划分：`GitKit`、`TimelineKit`、`AIKit`、`App`、`UI`。跨模块或无明确归属时省略。

### 3.4 摘要与正文

摘要：中文、祈使语气、不加句号。Git 术语保留英文——`feat(GitKit): 解析 porcelain v2 的 rename 记录`。

正文回答**为什么**：遇到什么问题、为什么选这个方案、放弃了哪些方案。涉及 git 边缘 case 的，写清触发条件——半年后你只会记得"有这么个坑"，记不得怎么复现。

### 3.5 粒度

- 一个 commit 一件事
- **每个 commit 都能独立通过测试**（bisect 的前提）
- 重构与功能改动分开提交
- 格式化改动单独提交，否则真实 diff 会被淹没

### 3.6 禁止项

- ❌ **任何 AI 协作署名**（`Co-Authored-By`、`Generated with`、🤖 等）——由 commit-msg hook 强制拦截
- ❌ 无意义摘要：`update`、`fix bug`、`修改`、`wip`
- ❌ 一次提交塞多个不相关改动
- ❌ 对已推送的 commit 做 `--amend` 或 rebase 后强推（除非只有自己在用该分支）

### 3.7 破坏性变更

type 后加 `!`，并在脚注写明迁移方式：

```
feat(GitKit)!: RepoActor.perform 改为接收 GitOperation 数组

BREAKING CHANGE: 单操作重载已移除，调用方改为传数组。
批量操作现在共享一次 HEAD 快照，避免中途状态不一致。
```

### 3.8 提交身份

本仓库通过 `git config --local` 固定为：

```
Monologuter <52441764+Monologuter@users.noreply.github.com>
```

**不要改全局配置**——同一台机器上的其他仓库使用不同身份。

邮箱必须用 GitHub 的 noreply 格式 `<账号ID>+<用户名>@users.noreply.github.com`。GitHub 靠 commit 里的 email 反查账号，用任何未在账号上验证过的邮箱（例如想当然的 `Monologuter@github.com`），commit 作者就只是一段纯文本：不可点击、不计入 Contributors、不计入贡献热力图。noreply 格式既保证关联成功，又不暴露真实邮箱。

验证是否关联成功（`author.login` 为 `null` 即未关联）：

```bash
gh api repos/<owner>/<repo>/commits --jq '.[0].author.login'
```

## 4. Swift 代码规范

### 4.1 格式化：swift format

Swift 6 工具链内置，**不引入 SwiftLint**——契合零依赖倾向。配置见仓库根 `.swift-format`。

```bash
swift format --recursive --in-place Packages/     # 格式化
swift format lint --recursive --strict Packages/  # 检查（hook 用）
```

### 4.2 命名

- 遵循 Swift API Design Guidelines
- 不缩写：`repository` 而非 `repo`。例外：文档中已固定的名字（如 `RepoActor`）
- 布尔属性用 `is` / `has` / `should` 前缀
- **Git 术语保留英文原词**：`stage`、`unstage`、`hunk`、`rebase`、`stash`——中文界面上也是如此（PRD 第 5 节本地化要求）

### 4.3 并发（Swift 6 严格模式）

- Package 保持 `swiftLanguageMode: .v6`，**不因为编译报错而降级**
- **每一处 `@unchecked Sendable` 都必须写注释说明凭什么安全**。这个标记关掉的是检查，不是问题本身
- **不要指望 actor 提供外部资源互斥**：actor 是可重入的，方法在 `await` 处挂起会释放执行权。需要真互斥（如独占 `index.lock`）时用显式队列，参见 `RepoActor.queueTail`
- 不在 async 上下文使用 `DispatchSemaphore` 等阻塞原语

### 4.4 错误处理

- 禁止 `try!`
- 禁止空 `catch {}` 静默吞错
- 用 `try?` 必须在注释里说明为什么这个失败可以忽略
- 面向用户的错误消息用中文，且**必须可操作**——告诉用户下一步做什么，而不只是陈述失败

### 4.5 强制解包

禁止 `!`，除非紧邻位置有不变量保证且写了注释。数组下标同理，优先 `first` / `indices.contains`。

### 4.6 访问控制与文档

- 默认 `internal`，跨模块才 `public`
- `public` API 一旦发布即为契约，破坏性修改走 §3.7
- **所有 `public` 类型与方法必须有中文文档注释**
- 注释解释**为什么**和**坑在哪**，不复述代码
- 已知边界与未处理场景必须显式写出（例：`ProcessRunner.readToEnd` 对孙进程继承管道的说明）
- 只给**有坑的**参数写 `- Parameter` 说明。`executable: 可执行文件路径` 这类复述签名的条目是噪音
- 会抛错的 public 方法应说明抛出哪些错误类型，返回值语义不显然时说明返回值

> 为此刻意关闭了 swift-format 的 `ValidateDocumentationComments` 规则：它要求文档结构完整（每个参数都写、每个返回值都有 `- Returns:`），机械执行的结果就是满屏复述代码的废话。文档质量靠 review 保证，不靠计数。
> 同样关闭 `UseLetInEveryBoundCaseVariable`：`case let .failed(code, message)` 比 `case .failed(let code, let message)` 更简洁，且是社区通用写法。

### 4.7 禁止项

- ❌ `print` 调试残留
- ❌ 注释掉的代码（git 有历史）
- ❌ 魔法数字（提取为具名常量）
- ❌ 无主的 TODO：TODO 必须带 issue 编号，否则删掉

## 5. 测试规范

### 5.1 分层

| 层 | 对象 | 特征 |
|---|---|---|
| 解析器单测 | 固定字节流 | 毫秒级、确定性、覆盖畸形输入 |
| 集成测试 | 真实临时 git 仓库 | 验证发出的命令参数正确 |
| 性能基准 | 大仓库 | 对齐 PRD 指标 |

### 5.2 铁律

- **每修一个 git 边缘 case，补一个 fixture 测试**
- **porcelain 样本必须从真实 git 采集，不照文档手写**——文档与实现存在出入，照文档写的测试会验证一个不存在的格式
- 修 bug 先写复现测试（红），再改实现（绿）。没见过测试失败，就不知道它是否真的在测那件事

### 5.3 确定性

测试禁止依赖：随机数、当前时间、网络、用户全局 git 配置、执行顺序、并发时序。

临时仓库必须设 `GIT_CONFIG_GLOBAL=/dev/null` 与 `GIT_CONFIG_SYSTEM=/dev/null`——否则用户的 `init.defaultBranch`、`commit.gpgsign`、hooks 会渗进测试，让结果时灵时不灵。

### 5.4 命名

用中文完整描述被验证的行为：

```swift
@Test("重命名记录缺少来源路径时报错而不是静默错位")
```

不要 `testRename1`。测试名是失败时唯一的线索。

### 5.5 准入门槛

- 新增 public API 必须有测试
- 涉及写操作、patch 生成、并发的改动必须有测试
- `swift test` 全绿才能推送（pre-push hook 强制）

## 6. 架构约束（三条铁律）

来自 `03-实现计划.md`，每次提交前自查：

1. **写操作单一入口**——所有改变仓库状态的 git 命令必须经 `RepoActor.perform(_:)`。直接用 `GitClient` 执行写命令就是在时间线上凿洞：那次改动将无法撤销，也不会出现在时间线里。
   - 自查：`grep -rn "client.run\|\.run(\[" --include="*.swift" Packages/ | grep -v Tests`
2. **操作自带元数据**——每个 `GitOperation` 必须有非空的中文 `summary`、`explanation`，以及正确的 `rewritesHistory` 标记。
3. **解析器与生成器同构**——`DiffParser` 解析出的结构，`PatchBuilder` 必须能还原成可 `git apply` 的 patch，用往返测试锁死。这是 hunk / 行级暂存不损坏用户文件的根本保证。

## 7. 安全与隐私

- API Key **只**存 Keychain。绝不落盘、绝不进日志、绝不进 UserDefaults
- `.env`、`*.pem`、`*.key`、`credentials*`、`id_rsa*` 等敏感文件的**内容永不进 AI prompt**，维护一份集中的过滤清单
- 日志只记录路径与操作类型，**不记录用户代码内容**
- 操作日志 `operations.jsonl` 不含文件内容
- **不擅改用户的 git 配置**。写入仅限两个自有命名空间：`<git-common-dir>/yugit/` 与 `refs/yugit/*`
- 提交前扫描：不得含 token、密钥、真实用户数据

## 8. 性能基线

PRD 第 5 节的指标转为可验证门槛：

| 指标 | 门槛 | 验证方式 | 生效版本 |
|---|---|---|---|
| 冷启动 | < 1s | 手动计时 | v0.3 |
| 5 万 commit 历史首屏 | < 500ms | 基准测试 | v0.3 |
| 历史滚动 | 60fps | Instruments | v0.3 |
| 内存占用 | < 500MB | Instruments | v0.3 |
| 外部改动响应 | ≤ 500ms | 集成测试 | v0.2 |
| 安装包体积 | < 30MB | 发布检查 | v0.5 |

性能敏感路径（历史加载、diff 渲染、status 刷新、快照打点）改动后必须重跑基准，**退化超过 10% 视为回归**，需在提交信息中说明原因或修复。

## 9. 依赖管理

**默认零第三方依赖。** PRD 承诺了 < 30MB 安装包与原生轻量，每个依赖都是对这个承诺的消耗，也是一份长期维护债。

引入任何依赖前必须书面回答（写在提交信息或 ADR 中）：

1. 解决什么问题？
2. 为什么不能自己写（工作量 vs 收益）？
3. 维护状态如何（最近提交、issue 响应）？
4. 许可证是否兼容商业闭源分发？

已明确排除：

- **libgit2 / SwiftGit2**——决策见实现计划（会切断用户的 credential helper / hooks 生态）
- **SwiftLint**——工具链自带的 `swift format` 已够用

允许但仍需论证：Apple 官方维护的 Swift 生态包（如 swift-collections）。

## 10. 文档规范

- `docs/` 用两位数编号，体现阅读顺序
- **决策变更时同步更新文档**。过期文档比没有文档更糟——它会让人基于错误前提做决定
- `CHANGELOG.md`：面向用户的变更记录，每个 tag 一节，中文书写
- 影响面大的技术决策记入 `docs/adr/NNN-标题.md`，格式为「背景 / 决策 / 后果 / 备选方案」
- `CLAUDE.md` 保持精简，只放无法从代码推导的约定

## 11. 发布流程

打 tag 前逐项确认：

- [ ] `swift test` 全绿
- [ ] `swift format lint --recursive --strict Packages/` 无输出
- [ ] 版本号已更新（SemVer + `CFBundleVersion` 递增）
- [ ] `CHANGELOG.md` 已更新
- [ ] 在 5 万 commit 的真实仓库上手测核心路径
- [ ] §8 性能指标达标
- [ ] 无敏感信息泄露（token、密钥、真实用户数据）
- [ ] Developer ID 签名 + 公证通过
- [ ] `spctl -a -vv <App>` 与 `xcrun stapler validate <App>` 均通过
- [ ] tag 已推送到远程

## 12. 质量门禁

### 12.1 本地 git hooks（现阶段主力）

| hook | 动作 | 失败后果 |
|---|---|---|
| `pre-commit` | 对暂存的 Swift 文件跑 `swift format lint --strict` | 阻止提交 |
| `commit-msg` | 校验 Conventional Commits 格式；拦截 AI 协作署名 | 阻止提交 |
| `pre-push` | `swift test` 全量 | 阻止推送 |

安装（克隆仓库后执行一次）：

```bash
./scripts/install-hooks.sh
```

hooks 本身不进版本控制（git 不跟踪 `.git/hooks/`），因此源文件放在 `scripts/hooks/` 并由安装脚本复制。

紧急情况可用 `--no-verify` 跳过，但**跳过后必须在下一个提交前补齐**。

### 12.2 CI（后补）

等 Xcode 工程建好、需要验证真机构建与签名时再加 GitHub Actions。

注意：私有仓库的 macOS runner 按 **10 倍速率**消耗免费额度（2000 分钟/月的额度实际只够约 200 分钟 macOS 构建）。因此 CI 只跑本地 hooks 覆盖不到的部分——真机构建、签名验证、多 macOS 版本矩阵。
